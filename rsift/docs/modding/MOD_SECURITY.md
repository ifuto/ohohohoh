# Mod セキュリティ (ハイジャック防止) — MOD_SECURITY

wave 195 で導入した、**悪意ある Mod があなたの PC を乗っ取るのを防ぐ**
多層防御の説明書です。ポイントは 2 つ:

1. **無断で危険なことをさせない** (サイレント乗っ取りの根絶)
2. **作れる Mod の幅は狭めない** (ゲーム API 全表面は無制限のまま +
   危険な機能も「承認」すれば使える)

---

## 仕組み (4 層)

### 第 1 層: ロード前の静的検査 (自動)

Mod の DLL/so/dylib をロードする**前に**、Rsift がバイナリを解析します:

- **import 表の構造解析** (Windows DLL): どの OS 機能を使うかを正確に列挙
- **文字列シグネチャ走査** (全 OS 共通): `powershell`、`/bin/sh`、SSH 鍵の
  パス、ブラウザのパスワード保存場所、自動起動キー等の痕跡を検出

検出結果は **8 種の「ホスト危険能力」**に分類されます:

| 能力 ID | 意味 |
|---|---|
| `process_exec` | 外部プログラムの起動 |
| `file_write_outside_scope` | ゲーム外フォルダへの書き込み |
| `file_read_sensitive` | 機密ファイル (パスワード/鍵) の読み取り |
| `network_egress` | ゲームサーバー以外への通信 |
| `native_module_load` | 追加ネイティブモジュールの読み込み |
| `jvm_instrumentation` | ゲームプログラム自体の書き換え |
| `input_capture` | キーボード/画面の監視 |
| `persistence_autostart` | PC 起動時の自動実行の登録 |

### 第 2 層: 即時ブロック (承認不可)

以下は**承認しても読み込めません** (理由つきで拒否されます):

- 認証情報窃取ツールの語彙 (mimikatz / sekurlsa / lsass ダンプ 等)
- プロセスインジェクション連鎖 (CreateRemoteThread +
  WriteProcessMemory 等の組み合わせ)

### 第 3 層: ユーザー承認 (consent)

危険能力を使う Mod は、**あなたが承認するまでロードされません**。

1. ロード時に「この Mod は ○○ の能力を要求しています」と表示され、
   Mod フォルダの `.rsift_mod_perms.json` に要求内容が自動記帳されます。
2. そのファイルを開き、許可したい能力を `requested` から `granted` に
   移して保存すると、次回からロードされます。
3. 記録には Mod ファイルの **SHA-256 ハッシュ**が紐付いています。
   **Mod を更新 (差替え) すると承認は自動的にリセット**されます
   (更新に紛れて悪性化する「すり替え」を防ぐため)。

`.rsift_mod_perms.json` の例:

```json
{
  "mods": {
    "minimap_plus": {
      "sha256": "8b3f…(自動記帳)",
      "granted": ["network_egress"],
      "requested": [],
      "denied": ["process_exec"]
    }
  }
}
```

### 第 4 層: 実行時ゲート + 監査ログ

ロード後も、Rsift のブリッジ経由で Mod が危険操作を実行するたびに能力を
再検査し、**許可/拒否の全件が監査ログに刻まれます** (直近 64 件保持)。
Java ブリッジ経由の特権コマンド (`host.` 系 op) は呼び出し元 Mod を
特定できないため、構造的に常時拒否です。

---

## 「作れる Mod の幅が狭まらない」理由 (設計保証)

- **普通の Mod (装飾・ワールド生成・レンダリング・ネットワーク・レジストリ・
  イベント・GUI …) は危険能力を一切使わない**ため、検査は一瞬で終わり
  **今までどおり何も変わらずロード**されます。ゲーム API 全 42 モジュールと
  全イベント/パケット経路に制限はありません (テストで機械的に固定済)。
- 危険能力が**本当に必要な Mod** (例: 外部ツール連携) も、上記の承認を
  経れば同じ機能を使えます。ブラウザの拡張機能の権限モデルと同じ考え方で、
  「無断」を禁止するだけで「機能」は禁止していません。
- 配布元が不明で信頼できない Mod 向けには、WASM サンドボックス層
  (`rsift-jvm` の wasm_sandbox) が最小権限の実行場所として併存します。

## Mod 開発者向け: 能力の宣言 (任意・推奨)

Mod に `<mod-id>.rsift-perms.json` を同梱すると、必要な能力を宣言できます:

```json
{
  "capabilities": ["network_egress", "file_write_outside_scope"]
}
```

宣言は承認を自動化するものではありませんが、ユーザーへの要求表示が
正確になります。未知の能力名は typo 防止のためエラーになります。
正式な能力 ID は上の表を使ってください。

---

## 正直な限界 (過剰な約束はしません)

- ネイティブ Mod はロード後はプロセス内のコードなので、**OS 操作そのものを
  実行時に禁じることはできません**。防御は「ロード前の検査と承認」が主戦場
  です (だから承認モデルと監査を厚くしています)。
- 検査はシグネチャ (既知の痕跡) ベースです。未知の手口や、ペイロードを
  暗号化して隠す高度な難読化はすり抜ける可能性があります。
- 承認した Mod は「信頼した」ことになります。配布元が不明な Mod は
  WASM サンドボックス層での運用を強く推奨します。

多層防御 (検査 + 即時ブロック + 承認 + ハッシュ固定 + 実行時監査) の
組み合わせで、**「何も知らずに乗っ取られる」事態を構造的に排除**するのが
本機能の目的です。
