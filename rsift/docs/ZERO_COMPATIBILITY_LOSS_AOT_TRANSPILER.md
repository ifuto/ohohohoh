## 2. Three Pillars of the AOT/JIT Transpiler

### 2.1. Stack-to-Register SSA Translation (`AotTranspilerEngine`)
Java bytecode operates as a stack machine (`iload_1`, `iload_2`, `iadd`, `ireturn`), which requires constant memory push/pop cycles. When `rsift-transpiler` reads a class via our SIMD parser, it instantaneously translates those stack operations into **Static Single Assignment (SSA) native register instructions** (`NativeOpcode`):
* Example: A bytecode sequence adding two integers is mapped directly to hardware registers (`mov eax, ecx; add eax, edx; ret`).
* Methods are stored in `transpiled_cache`, ready for direct C ABI function pointer execution!

### 2.2. Object Header & Layout Preservation (`CompatibleObjectHeader`)
The biggest secret to converting code without losing compatibility is **preserving the exact memory layout of Java objects**.
* Every transpiled native object generated by Rsift is prepended with a **16-byte JVM-compatible header** (`#[repr(C, align(8))]`), containing the 64-bit **Mark Word** and 64-bit **Klass Pointer**.
* Because the memory layout matches the JVM 100%, if an object is passed across a bridge or inspected via Java reflection, it behaves identically to a standard Java object. Nothing breaks!

### 2.3. Hot-Path Priority Promotion (`HotPathAotPromoter`)
Not all 50,000+ methods in Minecraft need instant compilation. Rsift automatically identifies **Hot-Paths**—methods executed thousands of times per second (e.g., `Mob.aiStep()`, `Level.tick()`, redstone propagation, block updates).
* These hot-path methods are immediately promoted to native AOT execution blocks (`is_hot_path = true`).
* The result: Your game rules and mod loops execute at bare-metal C/C++/Rust speed, completely bypassing the JVM!
