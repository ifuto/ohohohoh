# docs/ — Rsift ドキュメント分類ポリシー

**制定: 2026-07-24 / 根拠: ユーザー指示 (同日「docs/の中には…分けてほしい」)**
**保守: 指示の正本は `internal/USER_DIRECTIVES.md` と リポジトリルートの `UserSystemPrompt.md`**

本ディレクトリは読者別に 5 分類する。各文書は**読者に応じた情報粒度**を厳守し、
公開カテゴリには「読むだけで Rsift / RsGraphics を再実装 (パクる) ことができる」
粒度の情報を**書いてはいけない**。

## 1. 分類一覧

| ディレクトリ | 読者 | 書いてよいもの | 書いてはいけないもの |
| :--- | :--- | :--- | :--- |
| `modding/` | Rsift 上で **Mod を開発する人** | Mod の開発方法 (rsift-api の使い方、C-ABI 入口、ビルド・配置手順) | Rsift 本体の内部機構・実装設計 (読むだけで本体を再実装できる粒度) |
| `overview/` | **一般向け紹介** (製品を知りたい人) | 製品の価値・柱・互換性の目標・入手方法 | モジュール数、内部機構、アルゴリズム名、メモリ配置等のシステム詳細 |
| `user/` | **エンドユーザー** (プレイヤー) | 導入方法・操作方法・見た目の案内 | 実装詳細全般 |
| `ops/` | **リリース運用者** | 配布物の状態・配置手順・リリース運用情報 | エンジン設計の詳細 |
| `internal/` | **Rsift 開発者** (現状: プロジェクトオーナーのみ) | 全詳細可。**「読めばまんまパクれる」精細さを要求** — 監査レポート・設計・数学的導出・ベンチ証跡をここに集約 | (制限なし。但し検証済み事実と未検証主張の区別は必須) |

## 2. 判定基準 (「パクれない」の線引き)

- 読み手が文書だけから同等システムを再実装できてしまう粒度
  — アルゴリズムの具体的設計、ファイル/モジュール構成、数式・導出、
  メモリ配置、シェーダ実装、シーケンスの詳細 — は **すべて `internal/` のみ**。
- API の使い方、操作・導入手順、製品の価値・目標表明、公開互換性情報は
  各公開カテゴリ (`modding/` `overview/` `user/`) に書いてよい。
- **迷ったら `internal/`** (誤公開は取り返しがつかないため)。

## 3. 運用ルール

1. 新規文書は §1-2 の決め木で配置する。分類の追加はユーザー指示または
   本 README の更新をもって行う。
2. 公開カテゴリに内部詳細の混入を発見したら、該当節を `internal/` へ移動し
   公開側は概要への言及に留める。
3. 全文書で **検証済み事実と未検証の主張を区別**する (監査文化。
   根拠は `internal/AUDIT_2026-07-21_RSGFX_MODULES.md` の監査方法節を参照)。
4. `internal/` は機密相当。外部公開の判断はプロジェクトオーナーのみが行う。
